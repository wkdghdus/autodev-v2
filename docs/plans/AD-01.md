## RALPLAN-DR

### Principles

1. Fail closed on ambiguity: unknown authority, stale content, expired grants, mismatched identities, unsupported schemas, draft unknowns, invalid graphs, and missing evidence deny enable/dispatch.
2. Keep contract logic pure: lexical validation consumes explicit bytes; schema validation consumes parsed values and injected metadata snapshots/resolvers; no implicit discovery, target-content reads, writes, minting, approving, or dispatching.
3. Bind authority to content and context: generated config may request authority but cannot grant it; effective authority requires explicit trusted operator context plus content, epoch, expiry, revocation, project, and installation agreement.
4. Preserve independent state axes: aligned, enable-ready, and dispatch-ready are derived predicates over orthogonal axes, not aliases.
5. Preserve AD-00 evidence and current tests while recording AD-01 evidence honestly as offline/simulated unless live traces exist.

### Decision Drivers

1. AC2 and F02/F03/F08 require parser-observable, field/source-specific failures.
2. The repo is currently stdlib-only; adding a dependency requires explicit approval.
3. These contracts become future authority boundaries, so precise denial cases matter more than broad compatibility.

### Options

Option A: JSON-as-YAML subset. Smallest parser surface, but too narrow for normal PROJECT.yaml/EXECUTION.yaml block fixtures.

Option B: bounded stdlib YAML subset parser, favored. No dependency; supports needed fixture syntax; rejects unsafe syntax and duplicates with stable locations. It is deliberately not general YAML and needs token-aware tests.

Option C: pinned YAML parser dependency. Less parser maintenance, but violates current no-dependency default and expands trusted input handling without operator approval.

Decision: choose Option B. Support only indentation mappings/sequences, comments, quoted/unquoted scalars, integers, booleans, null, `[]`, `{}`, and simple inline string maps. Unsupported YAML fails closed.

### Pre-Mortem

1. Draft becomes dispatchable because predicates collapse into one boolean. Mitigation: exact formulas and progressive tests where missing evidence keeps later predicates false.
2. Provider name, filename, or generated config becomes authority. Mitigation: authority evaluation requires trusted operator context, matching digests, current grant/receipt, project+installation match, epoch match, and permission intersection.
3. Clone is adopted as same installation. Mitigation: compare project ID, installation ID, repo realpath, git common dir realpath, and slug independently; clone yields new installation required or conflict, never exact match.

## Orthogonal State Model

Enums: `RepositoryState=DRAFT|ALIGNED|INVALID`; `DeploymentState=ABSENT|CONFIGURED|PARTIAL|DRIFTED`; `CertificationState=NOT_RUN|PASSED|FAILED|STALE|BLOCKED_EXTERNAL`; `AdmissionState=ALLOW|DENY|UNKNOWN`; `ScheduleState=ABSENT|PAUSED|ENABLED|UNKNOWN`; `ExecutionState=IDLE|EXECUTING|WAITING_FOR_ANSWER|VERIFYING|FAILED_REPAIRABLE|UNCERTAIN|HUMAN_BLOCKED|VERIFIED_UNMERGED|INTEGRATED`; `ResourceState=AVAILABLE|BLOCKED_QUOTA|UNKNOWN`; `DeliveryState=NOT_TESTED|DELIVERED|FAILED|UNKNOWN`; `EnforcementAssurance=POLICY_ONLY|ENFORCED`.

Inputs also include `deployment_supported`, `required_validation_receipts_current`, `tested_delivery_current`, `operator_grant_current`, `grant_content_bound`, `approval_receipt_current`, `approval_content_bound`, `ownership_conflict`, `drift_conflict`, `eligible_approved_milestones`, `dependencies_satisfied`, and `base_policy_satisfied`. Missing evidence defaults to false/UNKNOWN; absent conflict evidence is unresolved and cannot count as a proven absence of conflict.

Formulas:

- `aligned = repository == ALIGNED`.
- `ready_for_enable = aligned and deployment == CONFIGURED and deployment_supported and certification == PASSED and required_validation_receipts_current and operator_grant_current and grant_content_bound and approval_receipt_current and approval_content_bound and enforcement == ENFORCED and delivery == DELIVERED and tested_delivery_current and not ownership_conflict and not drift_conflict`.
- `ready_to_dispatch = ready_for_enable and eligible_approved_milestones == 1 and dependencies_satisfied and base_policy_satisfied and execution == IDLE and admission == ALLOW and resource == AVAILABLE`.

Reason codes: `REPOSITORY_NOT_ALIGNED`, `DEPLOYMENT_NOT_CONFIGURED`, `CERTIFICATION_NOT_PASSED`, `OPERATOR_GRANT_MISSING_OR_STALE`, `GRANT_NOT_CONTENT_BOUND`, `APPROVAL_RECEIPT_MISSING_OR_STALE`, `APPROVAL_NOT_CONTENT_BOUND`, `ENFORCEMENT_NOT_ASSURED`, `DELIVERY_NOT_TESTED`, `OWNERSHIP_CONFLICT`, `DRIFT_CONFLICT`, `NO_ELIGIBLE_APPROVED_MILESTONE`, `MULTIPLE_ELIGIBLE_APPROVED_MILESTONES`, `DEPENDENCIES_UNSATISFIED`, `BASE_POLICY_UNSATISFIED`, `EXECUTION_NOT_IDLE`, `ADMISSION_NOT_ALLOW`, `RESOURCE_NOT_AVAILABLE`.

Additional reason codes: `DEPLOYMENT_UNSUPPORTED`, `VALIDATION_RECEIPTS_MISSING_OR_STALE`, `DELIVERY_RECEIPT_MISSING_OR_STALE`, `CONFLICT_EVIDENCE_UNKNOWN`. Unknown conflict facts must resolve to a denying conflict/unknown reason, rather than truthy/falsy coercion.

Readiness semantics follow pinned `autodev-v2/00-PROJECT-SPECIFICATION.md:163-182` (section 5, retrieved only to resolve enable versus dispatch). `DELIVERED` means a delivery test completed under separately authorized validation, before recurring work is enabled; it does not require a product milestone dispatch. Receipt applicability checks require matching current installation/project/profile/process generation, relevant config/skill/grant/authority hashes and revision/dirty fingerprint, freshness/expiry, successful cleanup, trace-backed LIVE evidence, and allowed observed effects. Synthetic PASS cannot certify a real installation; truth-table tests use explicitly labelled hypothetical inputs. AD-01 only consumes these facts and models ScheduleState; it performs no delivery test, scheduling, admission probe, or canary. Quota/admission are dispatch gates here; later actual enable commands must recheck their own scoped gates.

## Parser and Metadata Strategy

Split two layers:

1. Pure lexical/document parser accepts explicit bytes/string and returns parsed primitives plus source locations or issues. It performs no filesystem reads and no implicit discovery.
2. Schema validators accept parsed data plus injected `RepositoryMetadata`/resolver snapshot: repository root realpath, symlink/case-collision facts, digest map, current time, current deployment epoch, and current project/installation IDs. Path checks use this snapshot; no target content reads by default.

Parser rejects actual unsafe syntax but not safe quoted/plain literals. Tests must allow string values such as `hello!`, `R&D`, `*`, `<<`, quoted `---`, URLs, Unicode, and paths with spaces where valid while rejecting actual tag/anchor/alias/merge/document syntax. Parser tests include explicit input byte-size and nesting-depth limits.

Frozen records must normalize nested containers to immutable tuples or equivalent immutable structures so mutating original inputs cannot alter records.

## Authority Binding

Add `TrustedOperatorContext` with `operator_identity`, `now`, `project_id`, `installation_id`, `profile_identity`, `process_generation`, `deployment_epoch`, `source_digests`, `revocation_epoch`, `operator_grants`, `native_limits`, and `enforcement_limits`.

The trusted caller registry/store supplies grants and receipts plus trusted human issuance provenance. Parsed PROJECT values, parsed records, self-declared `human` strings, self-declared `operator_identity`, names, provider names, and filenames cannot bootstrap trust.

Effective permission is the minimum of requested permission, valid operator grant, native limit, and enforcement limit. Valid grants/receipts require matching project/installation IDs, matching deployment epoch, not expired, not revoked, exact content/source digest match, operation class/scope membership, and nonempty meaningful impact fields.

Negative tests cover stale content digest, expired grant/receipt, revoked epoch, project mismatch, installation mismatch, operation class mismatch, missing native/enforcement boundary, provider-name-only approval, filename-only approval, and valid-looking forged receipt not present in the trusted registry/store.

## ADR

Decision: implement AD-01 as a stdlib-only contracts package with immutable models, closed validators, a bounded YAML-subset parser, explicit injected metadata/resolver snapshots, trusted-context authority binding, exact readiness formulas, and preview-only migration.

Drivers: AC2/F02/F03/F08/F66 need field-specific fail-closed behavior; the repo currently has no dependencies; authority and identity records will gate later automation.

Alternatives: JSON-as-YAML-only is too narrow; adding a YAML dependency is convenient but requires explicit approval and broadens trusted input handling.

Why chosen: bounded stdlib parsing plus explicit metadata keeps the implementation auditable, testable, and aligned with the AD-00 offline posture.

Consequences: maintain a small parser and document it as an AutoDev subset, not YAML generally. Future parser replacement requires explicit approval and regression parity.

Follow-ups: execution writes `docs/verification/AD-01.md`; independent gate handles roadmap/manifest updates only after verification.
